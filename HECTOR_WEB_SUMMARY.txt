1. WHAT THE PROGRAM IS
--------------------------------------------------------------------------------

Hector 3.0 Web is a browser-only OOTP / StatsPlus analyzer. Users upload HTML
exports (Player List required; Draft Class and Team List optional). Hector
parses and scores players entirely in JavaScript in the browser.

Main surfaces:
  - Upload          — import HTML, field checklist, export guide screenshots
  - Pitchers/Batters — filters, ratings or stats Total, player cards
  - Draft           — separate amateur pool (Draft Class.html)
  - Teams           — org aggregates; optional Team List parks/standings
  - Compare         — side-by-side + radar
  - Trade / Contract — trade fairness, comps, $/WAR context
  - Options         — weights, StatsPlus URL template, “your team”
  - More menu       — Archetypes, League Analysis, Upcoming FA, Team Salary,
                      Hidden Gems (under construction), Glossary

Lineage: started from Hector 2.4.5 Beta (Python/Tkinter desktop). Evaluation /
discovery ideas were influenced by PortalOOTP (thanks to quarterback / Portal).
Scoring and tools were ported Python → JS. See CHANGELOG.md and README.md.


--------------------------------------------------------------------------------
2. HOW IT WORKS BEHIND THE SCENES
--------------------------------------------------------------------------------

Architecture is “static site + client-side engine.” There is NO application
server that scores players. A web server only serves files (HTML/CSS/JS/images).

Typical data flow:

  1. User opens index.html (Upload).
  2. Browser reads uploaded Player List.html (and optional Draft / Team List).
  3. parse.js (and related) turns HTML tables into player objects; disambiguates
     combined-export columns (e.g. batter vs pitcher CON, WAR, G).
  4. Upload checklist validates required / recommended fields against the export.
  5. pitchers.js / batters.js (and stats weight modules) compute Totals and
     component scores using weights from Options (localStorage).
  6. Large player arrays go to IndexedDB; settings/weights go to localStorage
     (key hector_v1). store.js hydrateState / rescore is the session hub.
  7. Other pages call requireData() via shell.js; if no roster, redirect Upload.
  8. UI pages (static/js/pages/*.js, live-filter.js, etc.) render tables, filters,
     cards, trade/contract tools. Glossary explains formulas.

Important privacy note: player data never leaves the user’s browser for scoring.
Hosting Hector only serves the app shell; each visitor’s uploads stay local to
that browser (IndexedDB). Clearing site data clears their roster.

Key folders:
  *.html                 — app pages at site root
  static/js/hector/      — parse, score, trade, contract, store, IDB, analytics
  static/js/pages/       — page controllers
  static/css/app.css     — styles
  static/img/            — Upload guide screenshots (export-guide/…)
  Dockerfile             — nginx:alpine image that copies the folder to html root

3. HOW IT IS SET UP AS A WEB APP TODAY
--------------------------------------------------------------------------------

Local (any OS with Node for a quick static server):

  cd hector-web
  npx --yes serve -p 8000
  # open http://localhost:8000

Or any static file server that serves the hector-web directory as document root
(paths are relative: pitchers.html, static/js/..., etc.). Clean URLs like /draft
work with some servers (e.g. serve); plain python -m http.server needs .html.

Docker already exists in-repo:

  cd hector-web
  docker build -t hector-web .
  docker run -p 8080:80 hector-web
  # open http://localhost:8080

Dockerfile: FROM nginx:alpine, COPY . → /usr/share/nginx/html, EXPOSE 80.
.dockerignore keeps junk like .venv out of the image.

No Python runtime is required for the live app. No database server. No build
step (plain ES modules in the browser). Optional: put the project on GitHub so
Linux and Cloudflare can pull the same tree.
